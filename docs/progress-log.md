# Журнал прогресса

## 2026-08-06

- Создана структура проекта (`docs/`, `scripts/`) и базовая документация.
- Инициализирован git-репозиторий, настроен `.gitignore` для локальных
  папок с большими/непубликуемыми файлами (`rootfs/`, `firmware/`,
  `images/`, `backups/`, `downloads/`, `build/`).
- Статус устройства: TWRP, остатки незавершённых попыток Windows 11 ARM
  (будут стёрты перед началом практических работ, после TWRP-бэкапа).
- Проведено исследование существующих community-наработок для dreamlte
  (Exynos8895/SM-G950F) — см. [prior-art.md](prior-art.md). Ключевые находки:
  - В mainline kernel.org в 2024 принята минимальная поддержка SoC/платы
    (CPU, pinctrl, GPIO, framebuffer, pstore).
  - Есть готовый вторичный загрузчик **uniLoader**
    (github.com/ivoszbg/uniLoader), специально поддерживающий dreamlte —
    снимает зависимость от внешнего UEFI. План загрузки полностью
    пересмотрен (см. boot-chain.md): план A теперь uniLoader + mainline,
    реюз стороннего UEFI понижен до плана C.
  - postmarketOS уже портирован (downstream-ядро 4.4.111): работают экран,
    тачскрин, батарея, WiFi, USB OTG; сломаны 3D-ускорение, звук, камера,
    Bluetooth, GPS, звонки/SMS/мобильный интернет. GNOME отмечен как
    "no longer works" (другие DE работают).
  - Есть заброшенный (с 2022) Halium-порт через libhybris — рабочий на тот
    момент почти по всей периферии, включая потенциальный путь к GPU через
    проприетарный blob.
  - **Критичная находка:** Mali-G71 официально не поддерживается драйвером
    Panfrost (по docs.mesa3d.org) — это теперь главный открытый блокер цели
    проекта ("графическое ускорение"), см. risks-and-open-questions.md и
    graphics.md.
- Дополнительно проверено (по запросу — рассматривался вариант "идти через
  Halium"): подключения GNOME Shell/Mutter к libhybris/hwcomposer нигде не
  существует. Известные libhybris-компоузеры — Qt/qtmir (Ubuntu Touch) и
  заброшенный с мая 2022 форк KWin `manjaro-libhybris/kwin-hybris`
  (архивный, ветка `hwc2`). В postmarketOS Halium-стек даёт только
  glamor-hybris (2D для X11), не Wayland/Mutter; сам Halium в pmOS
  рассматривают на предмет дропа из-за малого числа сценариев. Итог: путь
  через Halium даёт рабочий, но старый (2022) порт периферии — это реально
  оживляемый заброшенный проект — но GPU-бэкенд для Mutter поверх него
  нужно писать с нуля, ровно как и bring-up Panfrost под G71 в mainline.
  Ни один путь не даёт "GNOME + GPU" готовым из коробки.
- **Решение принято:** идём через bring-up Panfrost для Mali-G71 в mainline
  (план A boot-chain остаётся — uniLoader + mainline-ядро; Halium/libhybris
  отклонён как путь к GPU, но задокументирован для истории в prior-art.md).
  Причины: G71 расширяет уже поддерживаемый G72, а не пишется с нуля;
  Mutter получает GPU через родной DRM/KMS без доп. кода на стороне
  компоузера; путь остаётся полностью открытым без проприетарных блобов;
  результат может уйти в апстрим Mesa. Осознанная цена: периферию (тачскрин,
  звук, WiFi и т.д.), уже рабочую в старом Halium-порте, придётся портировать
  в mainline заново и отдельно от GPU-работ. Обновлены graphics.md,
  risks-and-open-questions.md, boot-chain.md, prior-art.md.
- Следующий практический шаг (ещё не начат): добиться initramfs shell на
  mainline-ядре через uniLoader (boot-chain.md план A) — предпосылка для
  начала работы над GPU.

- **По решению пользователя бэкап пропущен** — устройство переходит к

## 2026-08-07 — 🎉 ПЕРВАЯ УСПЕШНАЯ ЗАГРУЗКА MAINLINE-ЯДРА НА DREAMLTE

**План A из [boot-chain.md](boot-chain.md) достигнут: initramfs shell на mainline-ядре запущен на реальном железе.**

Путь до успеха:
- Тулчейн (aarch64-gcc, собранный вручную из .deb без root) не резолвил
  статические библиотеки (`libm.a`, `libmvec.a` — на самом деле линкер-скрипты
  с абсолютными путями `/usr/aarch64-linux-gnu/...`) — исправлено обёрткой
  `aarch64-linux-gnu-gcc`, инжектящей `--sysroot=<корень тулчейна>` (см.
  `build/toolchain/env.sh` и комментарий в обёртке).
- Статический BusyBox 1.36.1 собран тем же тулчейном; апплет `tc` не собрался
  из-за отсутствующих в актуальных заголовках ядра полей CBQ (qdisc давно
  выпилен из Linux) — апплет отключён, не нужен для минимального initramfs.
- Initramfs собран через `gen_init_cpio` (штатная тулза из исходников ядра) —
  единственный способ включить device-ноды (`/dev/console`, `/dev/null`) в
  cpio-архив без root на хосте.
- **Первая сборка uniLoader (52.8MB, с полным `defconfig`-ядром 51.5MB) не
  влезла в раздел BOOT (40MB).** Причина — стандартный arm64 `defconfig`
  тащит драйверы под ~50 других ARM64-платформ разом. Отключены все
  `CONFIG_ARCH_*` платформы кроме `ARCH_EXYNOS` (207→118 опций) — ядро
  ужалось до 27.7MB, uniLoader — до 29MB, итоговый boot.img — 33.6MB.
  Урок на будущее: для этого устройства всегда начинать с
  урезанного набора платформ, не с полного defconfig.
- Родной `BOOT` раздел (`/dev/block/sda7`, 40MB) прочитан и сохранён
  локально (`build/device-backups/boot_orig.img`, md5
  `4f4cccb4a8d40a3dc65a34b0482beeac`) — это единственная страховка вместо
  пропущенного полного TWRP-бэкапа.
- Новый boot.img собран путём точечного патча оригинала: заголовок
  (адреса, page_size, cmdline, appended Samsung DTB-блоб) не тронут,
  заменено только поле `kernel_size` и содержимое kernel-региона (на
  `uniLoader`). Итог — `build/device-backups/boot_new.img` (33.6MB, md5
  `1624eaf7cb52a6881ce1f1d90493c90a`).
- Прошито в `/dev/block/sda7` через `adb shell dd` прямо из работающей
  сессии TWRP (не Odin/heimdall — раз TWRP уже даёт root-shell, это проще).
  Побайтово проверено после записи (md5 совпал).
- После `adb reboot`: **на экране телефона появился реальный лог загрузки
  mainline-ядра** (Tux-пингвины, затем полноценный kernel log), дошёл до
  `Run /init as init process`, initramfs запустился и наш `/init`
  зациклился на `[initramfs] alive, uptime tick N` — ровно как задумано.

**Что уже подтверждено рабочим на этом этапе** (по логу с экрана):
- DRM/SimpleDRM — `simple-framebuffer cc000000.framebuffer: [drm] fb0:
  simpledrmdrmfb` — экран телефона реально показывает kernel console.
- `dwmmc_exynos` (UFS/MMC) контроллер инициализируется.
- `input: gpio-keys` — кнопки питания/громкости видны ядру.
- USB HID/storage core, IPv6-стек поднимаются без паники.
- Некритичные ошибки в логе (не блокируют загрузку, разобрать позже):
  `exynos-clkout probe fail (-22)`, предупреждение о device link у
  `samsung-pinctrl`.

## 2026-08-07 (продолжение) — тачскрин и кнопки заработали

- Патч для тачскрина (`samsung,s6sy761` на `hsi2c_23`, адрес 0x48,
  `interrupt-parent = &gpa1`, `usi9` в режиме I2C0_1, `reg_placeholder`
  фиктивный regulator до появления поддержки PMIC) **уже был смёржен в
  апстрим тем же автором** (Ivaylo Ivanov) на момент нашего клона — ничего
  добавлять в dts не пришлось, только включить
  `CONFIG_TOUCHSCREEN_S6SY761=y` в конфиге ядра (остальные зависимости —
  `I2C_EXYNOS5`, `EXYNOS_USI`, `REGULATOR_FIXED_VOLTAGE`, `INPUT_EVDEV` —
  уже были включены).
- `/init` расширен: после монтирования `/dev` печатает
  `/proc/bus/input/devices` и запускает `hexdump` на каждый
  `/dev/input/eventN` в фоне, чтобы события касания/кнопок были видны прямо
  на экране.
- Пересобраны ядро (с новым конфигом) → initramfs → uniLoader → новый
  boot.img (тот же метод точечного патча) → прошито → `adb reboot`.
- **Тачскрин отреагировал на касание, кнопка громкости — нет** (при первой
  проверке). Не стали гадать вслепую — попытка прочитать причину через
  pstore после захода в TWRP не сработала (TWRP использует свой собственный
  downstream-кернел с отдельной/несовместимой областью ramoops, лог
  mainline-ядра через него не виден — pstore не универсален между разными
  ядрами на одном устройстве, это стоит иметь в виду на будущее).
- Вместо этого — по первому же (более раннему) логу загрузки на фото уже
  было видно `input: gpio-keys as .../input0`, то есть драйвер кнопок
  регистрируется нормально. Значит дело не в ядре: `hexdump -C "$ev" | sed
  ...` в пайпе полностью буферизуется (glibc stdio ставит block-buffering
  вместо line-buffering, когда stdout — не терминал), и одно короткое
  нажатие кнопки (пара байт) просто не долетало до экрана, пока непрерывное
  касание экрана исправно заполняло и флашило буфер.
- Исправлено: `hexdump -C "$ev" > /dev/console &` напрямую, без пайпа.
  Пересобран только initramfs → uniLoader → boot.img (ядро и dtb менять не
  пришлось) → прошито → `adb reboot`.
- **Подтверждено: и тачскрин, и кнопка громкости работают.**

## 2026-08-07 (продолжение) — 🎉 рабочий Debian 13 (trixie) arm64 на телефоне

- Стадия 1 debootstrap (`--foreign --arch=arm64 --variant=minbase`, suite
  `stable` → резолвится в trixie) прогнана на хосте — 228MB, чисто
  (`var/lib/dpkg/status` пустой, ни одной записи).
- **USERDATA (`/dev/block/sda29`, 34.5GB) переформатирован под ext4**
  (раньше был FAT32 от прежних попыток с Windows — по прямому разрешению
  пользователя из самого начала проекта). Это теперь постоянное хранилище
  для Linux-rootfs на устройстве.
- Первая попытка стадии 2 — через `proot -0 -q qemu-aarch64-static` на
  хосте (эмуляция arm64 на x86_64) — не взлетела: proot не может
  по-настоящему выполнить `mount()` для procfs/sysfs, и dpkg спотыкался на
  "required read/write access to /var/lib/dpkg" из-за этого. Несколько
  неудачных повторов попытки **испортили общее состояние** — статус-файл
  dpkg накопил дублирующиеся записи о самом себе (каждый прерванный прогон
  дописывал поверх старого).
- **Переключились на нативный путь: chroot прямо в TWRP.** TWRP — это
  тоже arm64 Linux с настоящим root (подтверждено: `CapEff` — полный набор
  капабилити), так что chroot в arm64 Debian-rootfs не требует вообще
  никакой эмуляции. Ключевые грабли по пути:
  - `chroot новый_root команда` не сбрасывает `$PATH` — он наследуется от
    TWRP (Android-стиль, `/sbin` и т.д.), поэтому даже реально существующие
    в rootfs бинари (`grep`, `mount`) не находились. Фикс: явно
    `/usr/bin/env -i PATH=/usr/local/sbin:...:/bin HOME=/root
    DEBOOTSTRAP_DIR=/debootstrap chroot ...`.
  - Изначально казалось, что `mount -t proc` не работает даже под реальным
    root (permission denied) — но ручной тест (`chroot ... env PATH=...
    mount -t proc proc /proc`) сработал чисто. Настоящая причина ошибок —
    накопленная порча состояния от повторных попыток (испорченный
    `dpkg/status`), а не mount как таковой.
  - **Решение: чистый рестарт.** Пересобрали stage 1 с нуля на хосте
    (снова чисто, 0 записей в status), собрали ext4-образ сразу с
    rootfs внутри через `mke2fs -t ext4 -d rootfs -F rootfs.img` (populate
    прямо при создании ФС — экономит шаг распаковки на телефоне, где
    оказалась отдельная проблема: TWRP'шный `tar` (и even `busybox tar`)
    ловил OOM-killer при распаковке ~230MB на 3.5GB RAM устройстве —
    построение образа на хосте, где памяти много, обходит это полностью).
  - Образ (4GB, спарс ~218MB реальных данных) передан на телефон **без
    промежуточного сохранения** — `/tmp` на телефоне это tmpfs, не влезло
    бы; вместо этого стримили напрямую: `cat rootfs.img | adb shell "dd
    of=/dev/block/.../USERDATA"`.
  - `resize2fs` растянул ФС с 4GB до полных 34.5GB раздела.
  - `chown -R 0:0` — poправили владельца (fakeroot на хосте не пишет
    реальный root:root на диск, только подделывает то, что видят
    process'ы во время сборки; после переноса на телефон владелец был
    1000:1000 от нашего хостового пользователя).
- **`debootstrap --second-stage` через нативный chroot в TWRP прошёл
  полностью, без единой ошибки** — сконфигурировано 79 пакетов (dpkg, apt,
  bash, coreutils, util-linux, passwd/login и т.д.).
- Проверено: `chroot /mnt/userdata ... /bin/bash -c 'cat /etc/os-release'`
  → `PRETTY_NAME="Debian GNU/Linux 13 (trixie)"`, `dpkg --version` работает.
  **Это по-настоящему работающая, native arm64 Debian-система на самом
  телефоне.**
- `apt-get update` изнутри chroot не прошёл (`Temporary failure resolving
  deb.debian.org`) — у TWRP нет сети (recovery-режим, WiFi-драйвер не
  грузится). Не блокер: сеть появится, когда Debian будет грузиться через
  наше собственное mainline-ядро напрямую, а не через TWRP-chroot.

**Следующий шаг:** подключить `switch_root` в наш `/init` (initramfs), чтобы
mainline-ядро при загрузке через uniLoader переключалось из initramfs в этот
Debian-rootfs на USERDATA — то есть чтобы Debian реально ЗАГРУЖАЛСЯ, а не
был доступен только через TWRP-chroot. После этого — сеть (для apt) и,
по готовности, GNOME (пожелание пользователя; KDE Mobile — опция позже).

## 2026-08-07 (продолжение) — попытка switch_root: упёрлись в хранилище

- `/init` расширен: монтирует `LABEL=userdata` (ext4) и делает
  `exec switch_root /mnt/root /bin/bash /firstboot.sh`. Первая попытка —
  busybox `mount -L userdata` выдал usage/help: у busybox нет флага `-L`
  (это синтаксис util-linux), метка передаётся прямо в позиции устройства:
  `mount -t ext4 LABEL=userdata /mnt/root`. Поправлено.
- После фикса — `LABEL=userdata: Can't lookup blockdev`. Добавлена
  диагностика (`/proc/partitions`, `/dev` block-ноды, `dmesg`): в
  партициях **только loop0..7, ни одного `sda*`** — драйвер UFS (родное
  хранилище) не пробуется вообще.
- **Причина: в mainline dts для dreamlte просто нет device tree узла под
  UFS-контроллер** — драйвер собран (`CONFIG_SCSI_UFS_EXYNOS=y` и
  зависимости), но привязываться не к чему (только упоминания UFS в
  clock-именах в exynos8895.dtsi, самого узла контроллера нет). Патча под
  это в апстриме тоже не нашлось. Это не мелкая правка уровня тачскрина —
  нужны адреса регистров, PHY, clocks, которых у нас нет.
- **Обходной путь — microSD** (по подтверждению пользователя, физически
  вставлена в телефон; патч под неё от того же автора существует и
  теоретически смёржен). Отформатировали её через TWRP, добавили в dts
  `vmmc-supply`/`vqmmc-supply` (у `&mmc` было `/* TODO: Add regulators
  once PMIC is implemented */` — вообще без regulator'а).
  - Первая попытка — переиспользовать `reg_placeholder` (тот же, что у
    тачскрина) — получили `could not set regulator OCR (-22)`: голый
    `regulator-fixed` без `regulator-min/max-microvolt` не может отдать
    OCR mask. Завели отдельный `reg_sdcard` с `3300000` мкВ.
  - Ошибка регулятора ушла, но **карта всё равно не отвечает ни на одной
    частоте шины** (контроллер честно перебирает 300кГц→200кГц→100кГц —
    классический паттерн "нет ответа от карты", уже не про конфигурацию).
  - Пользователь переставил и переформатировал карту через TWRP — она

## 2026-08-07 (продолжение) — прямой интернет в TWRP через adb reverse + прокси

Пользователь спросил, нельзя ли просто зайти в сеть прямо с телефона вместо
qemu-эмуляции на хосте. У TWRP нет сетевых драйверов, но решение проще, чем
поднимать USB gadget networking — прокинуть TCP-порт через уже работающий
adb-канал:

- `tinyproxy` (только бинарник, `tinyproxy-bin`, без системной установки)
  запущен на хосте, слушает `127.0.0.1:8899`.
- `adb reverse tcp:8899 tcp:8899` — теперь `127.0.0.1:8899` внутри TWRP
  указывает на прокси на хосте, через уже существующий USB/adb-канал. Не
  нужны никакие сетевые драйверы на телефоне вообще — это чистый
  TCP-туннель поверх adb, не через IP-стек устройства.
- Прямой `wget` в TWRP через этот прокси сработал сразу.
- Настройка `apt` (`Acquire::http::Proxy "http://127.0.0.1:8899";`) в
  `/etc/apt/apt.conf.d/99proxy` — при первой попытке `apt-get update` внутри
  chroot поймали `Could not create a socket ... Permission denied`.
  Причина: apt пытается уронить привилегии на sandbox-пользователя `_apt`
  (которого нет), теряя Android-специфичную группу `inet` (GID 3003) —
  без неё ядро на этом устройстве запрещает создавать AF_INET сокеты
  (Android group-based network ACL). Фикс: `APT::Sandbox::User "root";` —
  не даём apt ронять привилегии, root уже в нужной группе.
- После этого фикса — новая, отдельная проблема: **проверка подписи
  репозитория проваливалась** (`sqv ... Not live until 2026-07-11...`) —
  у TWRP часы стоят на `Mon Jan 2 2017` (нет RTC-синхронизации в recovery).
  Исправлено вручную: `date -s '2026-08-07 10:35:00'`.
- **После обоих фиксов — `apt-get update` внутри нативного chroot в TWRP
  проходит чисто, без единой ошибки.** Дальше все установки пакетов будем
  делать этим путём (нативно, через прокси) вместо медленного qemu+proot
  на хосте — быстрее и не нужно вручную упаковывать/переносить .deb файлы.
- На практике host-скачивание через прокси (VPN хоста) оказалось медленным
  (122 kB/s — видимо, тот же VPN, что барахлил раньше в сессии). Пользователь
  раздал интернет с телефона (мобильные данные) на компьютер — после этого
  напрямую `curl` показал ~1 MB/s. Один пакет (`libsrtp2-1`) не докачался с
  первой попытки ("delayed item... failed" много раз подряд, транзиентный
  сбой), но в итоге всё равно оказался на диске рабочим.

## 2026-08-07 (продолжение) — первая реальная попытка bring-up UFS

По просьбе пользователя вернулись к паузе на storage — на этот раз опираясь
не на догадки, а на реальные даунстрим-исходники.

- Нашли даунстрим device tree UFS-узла
  (`Dyneteve/android_kernel_samsung_universal8895`, `exynos8895.dtsi`) —
  адреса регистров **подтверждены независимо**: `0x11120000` совпадает с
  тем, что мы уже видели живьём в пути TWRP
  (`/dev/block/platform/11120000.ufs/...`).
- Mainline уже поддерживает нужный класс контроллера в общем виде
  (`samsung,exynos7-ufs` в `drivers/ufs/host/ufs-exynos.c`), и в
  `include/dt-bindings/clock/samsung,exynos8895.h` уже есть готовые макросы
  именно под Exynos8895 (`CLK_GOUT_FSYS0_UFS_EMBD_I_ACLK` и т.д.) через уже
  рабочий `cmu_fsys0`.
- **Важное отличие от SD-карты:** питание UFS в даунстриме — простой
  GPIO-регулятор (`gpg0-0`, active-high), а не PMIC LDO. gpg0 как банк уже
  определён в `exynos8895-pinctrl.dtsi` (включён в основной dtsi) — тот же
  паттерн `regulator-fixed`, что уже дважды сработал для тачскрина/SD.
- **Приятный сюрприз:** вся низкоуровневая калибровка PHY (огромная таблица
  магических чисел в даунстриме) уже зашита в сам mainline-драйвер
  (`drivers/phy/samsung/phy-exynos7-ufs.c`) под `samsung,exynos7-ufs-phy` —
  переносить её не нужно. PMU isolation offset для PHY тоже не нужно
  указывать явно — при отсутствии второго значения в `samsung,pmu-syscon`
  драйвер берёт свой дефолт (`0x720` для этого варианта).
- **Настоящий блокер: PHY требует 4 отдельных тактовых сигнала**
  (`tx0_symbol_clk`, `rx0_symbol_clk`, `rx1_symbol_clk`, `ref_clk`) через
  строгий `devm_clk_bulk_get` (не optional). В mainline-драйвере тактов
  Exynos8895 таких выходов **не существует вообще** — только
  PCIe-referenced clocks в этой части clock-дерева. Это уже не пробел в
  dts, а пробел в самом clock-драйвере (`drivers/clk/samsung/
  clk-exynos8895.c`), для честного фикса нужны ещё биты регистров gate'ов,
  которых у нас нет.
- Добавили узлы `ufs`/`ufs_phy` на уровне SoC (`exynos8895.dtsi`, рядом с
  `cmu_fsys0`, по образцу `&mmc`) — регистры/клоки/PHY реальные и
  проверенные, кроме 3 из 4 PHY-клоков, куда временно подставили `&oscclk`
  как заглушку (чтобы `devm_clk_bulk_get` хотя бы не падал с ходу) — с явным
  пониманием, что это электрически неверно.
- **Результат первой попытки: полное зависание загрузки.** В логе на экране
  успели появиться `phy-samsung-ufs 11124000.phy: ...` строки (regulator
  "assuming enabled", "Icc-table-property not specified" — не фатальные) —
  то есть пробник PHY реально стартовал, `devm_clk_bulk_get` с
  заглушками-`oscclk` не упал сразу. Но баннер `initramfs is alive` так и
  не появился — зависло где-то в инициализации PHY/линка, скорее всего
  крутится в цикле опроса статус-бита, который никогда не установится с
  такими (электрически бессмысленными) тактами. Не опасно (софтверный
  залип, не порча железа) — исправлено форс-ребутом (Power+Volume Down)
  пользователем.
- **Откат:** `status = "disabled"` возвращён для `&ufs`/`&ufs_phy` в
  `exynos8895-dreamlte.dts`, пересобрано и прошито — стабильная загрузка
  восстановлена. Сами узлы `ufs`/`ufs_phy` в `exynos8895.dtsi` **оставлены**
  (отключённые) — это ценные, проверенные данные для следующей попытки, не
  нужно искать заново.

**Вывод:** UFS bring-up доведён до конкретного, узкого, понятного
препятствия — не "непонятно что не так", а "нужны 3 конкретных gate-клока в
clock-драйвере Exynos8895, которых там нет". Следующий реальный шаг —
либо добавлять эти клоки в `clk-exynos8895.c` (нужны биты регистров CMU_FSYS0,
не найдены пока), либо искать способ сделать `devm_clk_bulk_get` чисто
проваливающимся (а не зависающим) с отсутствующими/нерабочими клоками, чтобы
хотя бы диагностировать дальше безопасно.

## 2026-08-07 (продолжение) — 🎯 НАЙДЕНА КОРНЕВАЯ ПРИЧИНА: ядро само гасило FSYS0

Предыдущая гипотеза («не хватает 3 symbol-клоков в clk-exynos8895.c») —
**неверна**. Отдельный агент проверил даунстрим-исходники: таких гейтов у
Exynos8895 нет вообще, там всего 4 UFS-клока (aclk/fmp/unipro + мультиплексор),
ровно те, что уже есть в mainline. 4-клоковая модель PHY — это наследие
Exynos7420; все более новые Samsung SoC в mainline (autov9, autov920, gs101)
используют один `ref_clk`. То есть шаблон `samsung,exynos7-ufs-phy` изначально
был выбран не тот, но не это оказалось блокером.

### Как нашли настоящую причину

Ключевой сменой подхода стало **прекращение слепых перепрошивок**. Вместо
«собрать → прошить → зависло → форс-ребут» (один бит информации за цикл,
каждый раз с ручной перезагрузкой) сделали два инструмента:

1. **Драйверы UFS/PHY собраны модулями (`=m`), а не встроенными.** Встроенные
   пробуются во время загрузки, и зависание убивает весь boot без следов. Как
   модули они не грузятся сами — телефон гарантированно доходит до initramfs,
   а дальше мы грузим их по одному с маркерами до/после каждого шага.
2. **Прямое чтение регистров из шелла** через busybox `devmem` (потребовалось
   отключить `CONFIG_STRICT_DEVMEM`). Это позволило измерять железо вообще без
   пересборок ядра.

### Что показал замер

Первый замер опроверг гипотезу про такты в лоб: такты UFS **уже были включены**
(`ACLK/UNIPRO/FMP = 0x00300000`, бит 21 стоит), мультиплексор выставлен
(`0x10`), изоляция PHY снята (`ISOL = 0x1`) — а `CAP`/`VER` контроллера всё
равно читались нулями. Попытка выставить эти биты вручную ничего не меняла
(значение → то же значение).

Решающим стал второй замер — с положительным контролем и сканированием
соседних регионов:

| Регион | До | После `clk_ignore_unused pd_ignore_unused` |
|---|---|---|
| dwmmc VERID `0x1150006c` | `0x00000000` | `0x5342270A` |
| sysreg_fsys0 `0x11020700` | **Bus error** | `0x00000011` |
| UFS CAP `0x11120000` | `0x00000000` | `0x1303FF0F` |
| UFS VER `0x11120008` | `0x00000000` | `0x00000210` (UFSHCI 2.1) |

**Корневая причина:** S-Boot оставляет блоки FSYS0 включёнными (он сам только
что грузил ядро с UFS), а затем ядро на позднем этапе загрузки выполняет
`clk_disable_unused` + `genpd` cleanup и **выключает всё, что не заявил ни один
mainline-драйвер**. Обе строки были видны в логе с самого первого успешного
запуска — `clk: Disabling unused clocks` и `PM: genpd: Disabling unused power
domains` — но их значение мы поняли только сейчас.

Диагностический признак, который всё расставил на места: `sysreg_fsys0`
отдавал **bus error**, а UFS — тихие нули. Разные симптомы одной причины:
шинный интерфейс UFS ещё жив (aclk есть), а внутренняя логика уже мертва.

### Побочный результат: это же объясняет и microSD

`dwmmc VERID` читался нулём и стал осмысленным после того же флага. То есть
контроллер MMC был точно так же полумёртв — и это, скорее всего, и есть
причина, почему карта раньше «не отвечала ни на одной частоте шины»
(см. запись выше). Один флаг потенциально чинит обе истории с хранилищем.

### Текущее состояние

С `clk_ignore_unused pd_ignore_unused` (прописано в `chosen/bootargs`,
uniLoader сам cmdline не трогает — только патчит адреса initrd):

- PHY-модуль грузится **полностью чисто** (трассировка прошла все точки:
  probe → ioremap → syscon → phy_create → clks_init → provider_register, rc=0).
- `insmod ufs-exynos.ko` **зависает**, причём маркер `ufshcd_init enter` не
  печатается вообще — значит застревает ещё в `exynos_ufs_probe`/
  `ufshcd_pltfrm_init`, до инициализации ядра UFS.
- Зависание **недетерминированное**: точка остановки меняется от загрузки к
  загрузке, и после полного выключения питания прогресс стабильно дальше, чем
  после тёплого `adb reboot` (S-Boot по-разному оставляет блок).

Подозреваемый — шторм прерываний: в даунстриме UFS-прерывание описано как
`<0 334 0>`, а мы записали `IRQ_TYPE_LEVEL_HIGH`. Неверный тип срабатывания
даёт бесконечный шторм, что выглядит как зависание и хорошо объясняет
недетерминированность.

**Следующий шаг:** включены штатные детекторы (`SOFTLOCKUP_DETECTOR`,
`HARDLOCKUP_DETECTOR` + `ARM64_PSEUDO_NMI` с `irqchip.gicv3_pseudo_nmi=1`,
`DETECT_HUNG_TASK`) — вместо немого зависания ядро само напечатает стек с
именем функции, где застряло.

### Заметки по методике (пригодятся дальше)

- Проверять запись раздела нужно блоками по 512 байт с точным счётчиком:
  образ 35252224 байт = 8606.5 блоков по 4096, и `count=8606` читает на 2048
  байт меньше, давая ложное несовпадение MD5.
- `adb shell` портит бинарные данные; для чтения разделов только `adb exec-out`.
- fbcon на 1440×2960 без ускорения очень медленный, поэтому обильный вывод
  надо глушить (`dmesg -n 1`) и печатать компактно — иначе экран не прочитать
  с фотографии. Трассировочные маркеры ставим уровнем `pr_emerg`, чтобы они
  проходили при заглушённой консоли.

## 2026-08-07 (вечер) — UFS отложен, разворот на microSD

### Почему свернули UFS

После того как `clk_ignore_unused` оживил контроллер, драйвер всё равно
подвешивал систему — но **каждый раз в разном месте**, вплоть до зависания
внутри probe PHY-модуля, который вообще не трогает регистры. Это не похоже
на конкретную ошибку в настройке; это поведение блока, которому нужна
настоящая поддержка Exynos8895 (свой compatible, свои drv_data, свой
PHY-драйвер с реальной калибровкой), а не адаптация шаблона от Exynos7420.
Отдельный большой проект — вынесен за рамки текущей задачи.

Диагностика уперлась в отсутствие канала вывода:

- Штатные детекторы зависаний (`SOFTLOCKUP`/`HARDLOCKUP` + pseudo-NMI) не
  срабатывали ни разу — печатать было некому.
- Пользователь заметил, что **курсор перестаёт мигать**. Мигание рисует
  таймер ядра, так что это указывало на полную остановку. Но пользователь же
  и предположил обратное: возможно, умирает только вывод, а ядро живо.
  Проверить это было нечем — и это оказалось важнее самой гипотезы.
- Попытка читать ramoops из TWRP провалилась: в ядре TWRP отключён
  `CONFIG_DEVMEM` (`/dev/mem` нет, `mknod` даёт "No such device").
- Первая попытка показать лог из ramoops на экране выдала кашу: записи
  `dmesg` сжимаются (`.enc.z`). Исправлено отключением `PSTORE_COMPRESS` и
  фильтрацией вывода, но к тому моменту стало ясно, что дешевле сменить цель.

**Вывод по методике:** без нормального канала вывода отладка ядра на этом
устройстве превращается в гадание по фотографиям. В mainline есть узел UART
(`serial@10430000`), а у Samsung последовательный порт выведен на разъём USB
через MUIC — нужен кабель-джиг (резистор ~619 кОм между ID и землёй + USB-TTL).
В `bootargs` уже добавлено `console=ttySAC0,115200 console=tty0`, так что
консоль заработает сразу, как только такой кабель появится. USB-gadget как
альтернатива не годится: контроллера USB в mainline DT для этого чипа нет
вообще, это был бы ещё один bring-up с нуля.

### Разворот на microSD

Карта не работала ровно по той же причине, что и UFS, — и эта причина уже
исправлена: `dwmmc VERID` читался нулём до `clk_ignore_unused` и стал
`0x5342270a` после. Драйвер `dw_mmc` встроен в ядро, грузится сам, никаких
модулей и рисков зависания.

Подтверждено из TWRP: карта исправна, 8 ГБ, определяется как `mmcblk0`.
На ней были файлы пользователя (ColorOS-прошивка и патчи, NTFS, 100% занято) —
по явному разрешению пользователя карта отформатирована в ext4 с меткой
`userdata`, и на неё копируется готовый Debian с GNOME (3.5 ГБ) прямо из
внутренней памяти средствами TWRP.

Замечание по переносу: `cp -a` на телефоне идёт минуты и переживает разрыв
управляющей команды только если запущен через `nohup` в фоне — иначе таймаут
на стороне ПК убивает и копирование.

**Следующий шаг:** загрузиться с прошитым образом (модули UFS не грузятся —
зависать нечему) и проверить, видит ли ядро `mmcblk0`. Если видит —
`switch_root` в Debian и цель достигнута.

## 2026-08-07 (поздний вечер) — microSD: питание найдено, чтение данных не работает

Разворот на карту дал ощутимый прогресс, но упёрся в новую стену.

### Найдено и исправлено: питание карты

Симптом был: контроллер жив (`VERID = 0x5342270A`), видит вставленную карту
(`Got CD GPIO`), честно снижает частоту 400→300→200→100 кГц — и не получает
ответа. Это классическая картина обесточенной карты.

Причина: в DT питание было описано пустышкой `regulator-fixed` без GPIO,
которая физически ничего не включает. Настоящих регуляторов у нас нет —
в mainline **отсутствует поддержка PMIC S2MPS17 и шины SPEEDY**, по которой
он подключён.

Ключ нашёлся эмпирически, без гадания: TWRP работает на даунстрим-ядре, где
карта исправна, и там доступен `/sys/kernel/debug/gpio`:

```
gpio-121 (vmmc)     out hi
gpio-225 (ufs-vcc)  out hi
```

Плюс таблица банков (`GPIOs 120-123 ... gpb1`, `225-226 ... gpg0`) дала
перевод в термины DT: **vmmc = gpb1-1**, ufs-vcc = gpg0-0 (последнее
подтвердило, что для UFS мы угадали верно). Заодно из
`/sys/kernel/debug/regulator/regulator_summary` стало видно разделение:
`vmmc` — это GPIO-ключ, а `vqmmc` — настоящий LDO PMIC, который uniLoader
уже включает на 2.8 В перед стартом ядра (поэтому UHS-режимы отключены —
переключать 1.8 В нам нечем).

После добавления `gpio = <&gpb1 1 GPIO_ACTIVE_HIGH>` карта **определилась**:
`mmc0: new SDHC card at address 0007`, `mmcblk0: SD8GB 7.23 GiB`.

**Урок методики:** снимать состояние с работающего даунстрим-ядра через
debugfs оказалось быстрее и надёжнее, чем искать даунстрим-исходники (нужный
board dts для dreamlte в доступных форках отсутствует).

### Не решено: любая передача данных проваливается

```
I/O error, dev mmcblk0, sector 0 op 0x0:(READ)
mmcblk0: unable to read partition table
READ FAILED: dd: /dev/mmcblk0: Input/output error
```

Опознание работает (команды идут), данные — нет. Проверенные и **отвергнутые**
гипотезы:

- **Таблица разделов.** Сначала на карте была GPT; переписали её обычной MBR,
  указывающей на тот же начальный сектор 2048 (данные не пострадали,
  `blkid` и файлы Debian на месте). Не помогло — раздел всё равно не
  появляется, потому что не читается сам сектор 0.
- **DMA.** Драйвер в этой версии ядра **игнорирует** документированное
  свойство `fifo-mode` и берёт режим передачи только из регистра HCON.
  Пропатчили `dw_mmc.c`, чтобы свойство работало; подтверждено в логе
  (`fifo-mode requested, using PIO`). Чтение всё равно падает — **DMA ни при
  чём**, несмотря на 64-битный IDMAC и память выше 4 ГБ.
- **Разрядность/скорость.** С `bus-width = <1>` и `max-frequency = <4000000>`
  симптом сменился: вместо быстрой ошибки чтение стало **зависать**.

Открытые подозрения (переданы в исследование):

- **Частота контроллера.** У нас `Bus speed = 41640625Hz` (= 666.25 МГц / 16),
  хотя DT просит `clock-frequency = <800000000>`; у даунстрима — 25 МГц,
  затем 200 МГц. `assigned-clock-rates` в узле не задан вообще.
- **Подтяжка на линиях данных.** В mainline `sd2_bus1`/`sd2_bus4` (gpj0-2..5)
  идут с `EXYNOS_PIN_PULL_NONE`; сравнить с даунстримом не удалось (в ядре
  TWRP нет ни pinctrl-debugfs, ни `/dev/mem`).
- Поддержка microSD для этой платы попала в mainline патчем 2025 года, и
  неизвестно, подтверждал ли кто-нибудь её работу на живом железе.

### Прочее

- Debian (3.5 ГБ, с GNOME) скопирован из внутренней памяти на карту
  средствами TWRP и проверен: `e2fsck` чист, `gnome-shell`/`systemd`/
  `firstboot.sh` на месте. Карта отформатирована в ext4 с меткой `userdata`
  по явному разрешению пользователя (на ней были его файлы ColorOS).
- Долгие копирования на телефоне нужно запускать через `nohup` в фоне —
  иначе таймаут управляющей команды на ПК убивает и сам `cp`.

## 2026-08-07 (ночь) — microSD: сужено до одной точной ошибки, но не решено

Запущен агент-исследователь по проблеме чтения с карты. Отчёт оказался очень
полезным и дал сразу несколько подтверждённых на железе улучшений, но
корневую причину закрыть не удалось.

### Что агент нашёл и что подтвердилось

**Патч поддержки microSD для этой платы, судя по всему, никогда не проверяли
дальше опознания карты.** Он принят в mainline (коммит `2e7281e60a6b`), и в
его же описании автор пишет: «поскольку основной PMIC пока не поддержан,
предполагаем, что нужные регуляторы включены предыдущим загрузчиком». Мы
доказали, что для VMMC это неверно — питание пришлось включать самим через
GPIO. То есть данные с карты в mainline на этом устройстве, вероятно, ещё
никто не читал.

**Исправлена моя ошибка в расшифровке таймингов.** Я считал, что наши
`samsung,dw-mshc-sdr-timing = <0 3>` совпадают с вендорскими. На самом деле
`SDMMC_CLKSEL_TIMING()` упаковывает их как sample=timing[0], drive=timing[1]
(обратно тому, что подсказывает формулировка «tx/rx» в биндинге). Вендорский
лог печатает `CLKSEL = 0x03030003`, то есть sample=3 — значит нужно `<3 3>`.

**Исправлена частота контроллера — и это подтвердилось на железе.** В узле не
был задан `assigned-clock-rates`, из-за чего делитель оставался произвольным,
а `fout_shared4_pll` бутлоадер оставляет на 666.25 МГц. Итог: `bus_hz`
= 41.64 МГц. Переключение на `fout_shared2_pll` (ровно 800 МГц) с явным
`assigned-clock-rates = <0>, <800000000>` дало **ровно 50 МГц**, как у
вендора. Плюс добавлен `cap-sd-highspeed` (его выставляет только DT, не
драйвер) — карта перешла в высокоскоростной режим:
`mmc0: new high speed SDHC card`.

**Добавлена подтяжка на CMD/DAT** — exynos8895 оказался единственным Exynos в
дереве, где линии данных карты оставлены без подтяжки (7420, 5433, 7870 все
подтягивают). Проверено чтением регистров: применилась корректно.

### Точный диагноз ошибки

Поднят уровень диагностического сообщения драйвера (`dev_dbg` → `dev_err`,
`dw_mmc.c:1833`), потому что `CONFIG_DYNAMIC_DEBUG` в конфиге нет:

```
dwmmc_exynos 11500000.mmc: data error, status 0x0000020c
```

`0x20c` = CMD_DONE | DTO | **DRTO (бит 9)**. То есть команда ушла, а карта
**вообще не начала передавать данные** — это не искажение и не CRC.

Ключевое наблюдение (из анализа агента): опознание карты
(`mmc_sd_setup_card`) само делает три чтения данных — SCR 8 байт, SSR 64
байта, SWITCH 64 байта, — и все они **обязаны** были пройти, иначе `mmcblk0`
не появился бы. Значит путь данных в принципе рабочий. Падают только
**секторные чтения по 512 байт**, причём одинаково на 50 МГц и на 3.47 МГц,
в 4-битном и 1-битном режиме, через DMA и через PIO.

### Проверено и отвергнуто (каждое — измерением, не рассуждением)

| Версия | Как проверено | Итог |
|---|---|---|
| DMA (64-битный IDMAC, память выше 4 ГБ) | пропатчен `dw_mmc.c`, чтобы работало штатное свойство `fifo-mode`; подтверждено `Using PIO mode` | не при чём |
| Таблица разделов (GPT) | переписана обычной MBR на тот же сектор 2048; `blkid` и файлы Debian на месте | не при чём — не читается сам сектор 0 |
| Блок защиты памяти (SMU) | прочитаны регистры `0x11501200/04/0c` — все нули, запись **не прижилась** ни от драйвера, ни вручную | блока по этому адресу просто нет; в DT для слота карты указан тип контроллера от eMMC |
| Подтяжка на линиях данных | прочитан регистр `0x11430028` = `0x00001FFC` — подтяжка стоит; `CON 0x11430020` = `0x00222222` — ножки на функции 2 | применено верно, не помогло |
| Разрядность и частота шины | 1 бит + 4 МГц → симптом сменился с быстрой ошибки на длинный таймаут (это тот же DRTO, таймер ~4.8 с) | не при чём |
| Размер буфера FIFO | убрано `fifo-depth = <64>` из dtsi, чтобы драйвер определил его сам из FIFOTH | не помогло |

Механизм, который казался самым убедительным и всё же не подтвердился:
`dw_mci_ctrl_thld()` ставит порог чтения равным размеру блока, если
`blksz/8 <= fifo_depth`; при заявленных 64 ячейках 512-байтовое чтение
требует освобождения всего буфера целиком, тогда как 8- и 64-байтовые
проходят с запасом. Красиво объясняло бы ровно наш случай — но автоопределение
глубины ничего не изменило.

### Ошибки, которые я допустил по ходу (чтобы не повторять)

- Прочитал регистры ножек по адресам банка `gpj0` **другого чипа** (8890
  вместо 8895): у 8895 этот банк смещён на `0x020`, а не на `0x000`. Первый
  замер показал «ножки не настроены», что было неверно и стоило лишнего круга.
- Забыл смонтировать `debugfs` перед обращением к нему — диагностический
  вывод в одном из заходов оказался пустым.

### Где остановились

Состояние карты сейчас: определяется как `SD8GB 7.23 GiB` в высокоскоростном
режиме на 50 МГц, ножки и питание подтверждённо верны, но любое чтение
сектора заканчивается DRTO. Debian (3.5 ГБ, с GNOME) лежит на карте готовый.

**Реалистичные пути дальше:**

1. **Аппаратная консоль через UART.** В mainline есть узел `serial@10430000`,
   у Samsung последовательный порт выведен на разъём USB и включается
   кабелем-джигом (резистор ~619 кОм между ID и землёй + USB-TTL). В
   `bootargs` уже прописано `console=ttySAC0,115200 console=tty0`, так что
   заработает сразу. Это даст полный лог в реальном времени вместо
   фотографирования экрана и радикально ускорит любую дальнейшую отладку.
2. **Написать автору патча.** У нас на руках образцовое описание дефекта:
   его microSD-патч не способен передавать данные, VMMC требует GPIO
   `gpb1-1` (в патче это не учтено), плюс найденные исправления по частоте и
   `cap-sd-highspeed`. Это ценный вклад в апстрим независимо от того,
   починим мы сами или нет.

## 2026-08-07 (ночь) — 🎉🎉 microSD ЧИТАЕТСЯ, Debian ЗАГРУЖАЕТСЯ через switch_root

**Главная цель «Debian грузится нашим собственным mainline-ядром» достигнута.**

### Корневая причина: таймаут данных, а не передача данных

`dw_mci_set_data_timeout()` в общем драйвере пишет счётчик таймаута как
`TMOUT[31:8]`. На Exynos8895 поле `TMOUT[10:8]` — **не младшие биты счётчика,
а множитель**. Эффективный таймаут там считается как
`((TMOUT[10:8] - 1) * 0xFFFFF) + TMOUT[31:11] * 8`.

Пока счётчик не кратен восьми, в поле множителя случайно попадает что-то
ненулевое, и всё работает. Как только счётчик кратен 8 — множитель ноль,
`n - 1` уходит в минус, таймаут истекает мгновенно. Драйвер видит DRTO при
`TCBCNT == 0` и честно докладывает «карта вообще не начала передавать
данные» — при том, что карта в этот момент исправно ждала команды.

Отсюда вся видимая асимметрия, которая столько времени выглядела как
проблема размера передачи:

| Что | Частота | Счётчик | В поле множителя | Итог |
|---|---|---|---|---|
| опознание карты (SCR/SSR/SWITCH) | 396 825 Гц | 39 683 | 3 | работает |
| секторные чтения | 50 МГц | 5 000 000 | 0 | DRTO |
| старый «медленный» тест | 3.47 МГц (`bus_hz` 41.64 МГц) | 347 000 | 0 | DRTO |

Поэтому и не помогало **ничего** из проверенного раньше: ни DMA против PIO,
ни ширина шины, ни тайминги, ни питание, ни SMU. Карта всё это время
исправно отвечала `r1 00000900` и молчала по данным просто потому, что
контроллер прекращал ждать сразу.

### Правка

Новый `exynos8895_drv_data` с `.set_data_timeout` / `.get_drto_clks` (обе
функции уже были в драйвере — их используют «квиркнутые» контроллеры) и
запись `samsung,exynos8895-dw-mshc-smu` в таблицу совпадений
(`dw_mmc-exynos.c`). `DW_MMC_QUIRK_EXTENDED_TMOUT` **намеренно не
выставлен**: он подавляет DTO, которого квиркнутые контроллеры не выдают, а
этот выдаёт — в наших ошибках был статус `0x20c`, то есть DRTO вместе с DTO.

Все патчи выгружены в репозиторий: [../patches/kernel/](../patches/kernel/)
(база — `0d8395707`, v7.2.0-rc6), конфиг ядра —
[../configs/dreamlte_defconfig](../configs/dreamlte_defconfig),
скрипты — [../patches/initramfs/](../patches/initramfs/).

### Что подтверждено на живом железе (лог с экрана телефона)

```
mmc_host mmc0: Bus speed = 50000000Hz (req 50000000Hz, actual 50000000HZ div = 0)
mmc0: new high speed SDHC card at address 0007
mmcblk0: mmc0:0007 SD8GB 7.23 GiB
mmcblk0: p1
   sector 0 read OK, first bytes: ...
   MBR signature: 55aa  (expect 55aa)
   mounted /dev/mmcblk0p1
   Debian found - switching root
==================================================
 Debian rootfs is alive (switch_root succeeded)
PRETTY_NAME="Debian GNU/Linux 13 (trixie)"
==================================================
[debian] alive, uptime tick 1
[debian] alive, uptime tick 2
```

То есть: карта опознаётся в high-speed на 50 МГц, сектор 0 читается,
таблица разделов разбирается, ext4 монтируется, `switch_root` в Debian 13
проходит, и rootfs с SD-карты реально исполняется как корневая ФС.

### Заодно закрыто: SMU был ни при чём

В том же диагностическом прогоне видно, что сектор 0 **прочитался ещё до**
ручной перезаписи регистров SMU, а сами регистры (`0x11501200/04/0c`)
читаются нулями и запись в них не приживается. Блока защиты по этому адресу
у слота карты просто нет — гипотеза окончательно снята.

### Оговорка по состоянию прошивки

Лог выше получен с образа `boot_tmout.img` — это proof-of-concept с
хардкодом `0xFFFFFFFF` в таймаут. Штатная версия правки собрана в
`build/device-backups/boot_sdworks.img` (md5 `ae38e736d4015296ebb252b5e492f14c`),
но **на устройство ещё не прошита** — проверено чтением `/dev/block/sda7` и
сравнением md5 (совпал с `boot_tmout.img`). Её надо прошить и убедиться, что
чистая правка ведёт себя так же.

### Что осталось открытым и к делу не относится

- `DW_MMC_QUIRK_FIFO64_32` для 8895 (HCON заявляет 64-битный FIFO, PIO из-за
  этого читает мусор; на DMA-путь не влияет).
- SDR104, который downstream использует на 200 МГц — для него нужен реально
  переключаемый `vqmmc`, то есть поддержка PMIC S2MPS17 и шины SPEEDY.

### Ограничения загруженной системы, которые надо держать в голове

Когда Debian грузится нашим ядром, у него **нет ни USB, ни сети**: узла
USB-контроллера в mainline DT для этого чипа нет вообще, WiFi тоже не
поднят. Значит `adb` в этом окружении недоступен, внешнюю клавиатуру
подключить нельзя, и `apt` не работает. Ввод — только тачскрин и
кнопки громкости/питания; вывод — только экран. Всё, что нужно системе,
готовится заранее из TWRP, а логи надо писать на саму карту (persistent
journal), иначе после зависания их будет неоткуда взять.

## 2026-08-07 (ночь, продолжение) — переход от тестового init к настоящему systemd

Всё, что ниже, следует из одного факта: **у загруженной системы нет ни
клавиатуры, ни сети, ни adb**. Поэтому сеанс должен подниматься сам, без
единого нажатия клавиши, а диагностика — оставаться на карте.

- `/init` в initramfs переписан ([../patches/initramfs/init](../patches/initramfs/init)):
  диагностические дампы регистров убраны (своё они отработали), вместо
  `firstboot.sh` — `exec switch_root /mnt/root /sbin/init`. Ожидание
  появления `mmcblk0p1` сделано циклом до 30 секунд вместо фиксированного
  `sleep`; служебные ФС переносятся в новый корень через `mount -o move`.
- Rootfs на карте подготовлен скриптом
  [../scripts/setup-rootfs-session.sh](../scripts/setup-rootfs-session.sh),
  выполненным нативно в chroot из TWRP:
  - **journald `Storage=persistent`** + `/var/log/journal` — единственный
    способ узнать, что пошло не так; читается из TWRP после перезагрузки;
  - пользователь `phone` (группы `sudo,video,input,audio,render,plugdev,netdev`)
    и **автовход GDM** — пароль набрать физически нечем, экранная клавиатура
    появляется только внутри уже запущенного сеанса GNOME;
  - `graphical.target` по умолчанию, сеанс — GNOME на Wayland (Xorg не
    ставился, в `/usr/share/wayland-sessions` только `gnome`);
  - замаскированы `NetworkManager-wait-online` и
    `systemd-networkd-wait-online` — сети нет, каждый такой юнит это
    +90…120 секунд на загрузку;
  - `LIBGL_ALWAYS_SOFTWARE=1` / `GALLIUM_DRIVER=llvmpipe` — GPU не
    поддержан ничем, единственный экран это SimpleDRM;
  - `Restart=no` для `gdm3.service` — иначе при неудаче GDM крутится в
    вечном перезапуске и затирает экран, не давая ничего прочитать;
  - `fstab` с `passno=0`: `e2fsprogs` в этот rootfs не ставился, `fsck.ext4`
    в системе нет, и с `passno=1` `systemd-fsck-root` падал бы каждый раз.
- Грабли по пути: стоковый `/etc/gdm3/daemon.conf` уже содержит строки
  `AutomaticLoginEnable = true` **закомментированными**, поэтому проверка
  «есть ли уже такая строка» срабатывала на комментарий, и автовход тихо не
  включался. Файл теперь переписывается целиком.
- Сборка образа сведена в скрипт
  [../scripts/build-boot.sh](../scripts/build-boot.sh) (initramfs →
  uniLoader → boot.img через `repack-bootimg.py`). Отдельная тонкость: у
  uniLoader каталог называется `arch/aarch64`, поэтому `ARCH=arm64` из
  `toolchain/env.sh` (он для ядра) ломает его сборку — нужен `ARCH=aarch64`.
- `build/device-backups/boot_gnome.img` (md5 `0ac27812033ffe33e5d3954fc6e2db12`)
  — штатная правка таймаута + новый initramfs — прошит в `/dev/block/sda7` и
  побайтово проверен, карта размонтирована начисто, устройство перезагружено.

## 2026-08-07 (ночь) — 🎉🎉🎉 РАБОЧИЙ СТОЛ GNOME ЗАПУСТИЛСЯ НА ТЕЛЕФОНЕ

**Основная цель проекта достигнута с первой попытки: телефон загрузился в
рабочий стол GNOME 48 на Debian 13, под нашим собственным mainline-ядром.**

Цепочка целиком, без единого проприетарного блоба:

```
S-Boot → uniLoader → mainline Linux 7.2.0-rc6 → initramfs (busybox)
       → switch_root → systemd 257 → GDM (автовход) → GNOME Shell 48.7 (Wayland)
```

Подтверждено пользователем визуально: на экране рабочий стол GNOME. Штатная
(не proof-of-concept) правка таймаута данных подтвердилась в бою — карта
читается на протяжении всей загрузки, а это тысячи секторных чтений, а не
один `dd`.

Что осталось непроверенным на этот момент: отзывчивость (рендеринг
программный, `llvmpipe` на 1440×2960 — это заведомо медленно), работа
касаний внутри сеанса, экранная клавиатура.

**Оставшаяся часть исходной цели — аппаратное ускорение.** Сейчас всё
рисует CPU. Mali-G71 не поддержан Panfrost, и это следующий (и последний
крупный) блокер, ради которого проект и затевался.

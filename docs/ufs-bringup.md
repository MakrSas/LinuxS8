# Bring-up UFS на dreamlte (SM-G950F, Exynos8895)

**Цель:** отвязаться от microSD — чтобы Debian жил на внутренней памяти
телефона (34.5 ГБ), а не на карте.

Документ самодостаточный: по нему можно продолжить работу с нуля, не читая
переписку. Журнал по датам — в [progress-log.md](progress-log.md).

---

## 1. Где мы сейчас

**2026-08-08: bring-up UFS завершён. Внутренняя память работает.**

```
exynos-ufshc 11120000.ufs: Power mode changed to : FAST series_B G_3 L_2
scsi 0:0:0:0: Direct-Access     SAMSUNG  KLUCG4J1ED-B0C1  0003 PQ: 0 ANSI: 6
sd 0:0:0:0: [sda] 15616000 4096-byte logical blocks: (64.0 GB/59.6 GiB)
sd 0:0:0:0: [sda] Write cache: enabled, read cache: enabled, supports DPO and FUA
sda: sda1 sda2 sda3 ... sda29
sd 0:0:0:0: [sda] Attached SCSI disk
```

`FAST series_B G_3 L_2` — это HS Gear 3, две линии, серия B, то есть
максимум для UFSHCI 2.1, а не аварийный запасной режим. Кроме `sda`
поднялись служебные LU: `sdb` (4.19 МБ), `sdc` и `sdd` (по 8.39 МБ) — это
загрузочные разделы UFS, плюс три well-known LUN.

| Что | Состояние |
|---|---|
| Debian 13 + GNOME 48 | **работает**, грузится с microSD (`mmcblk0p1`, метка `userdata`) |
| Внутренняя память (UFS) | **работает**, HS-G3 ×2 rate B, 64 ГБ, `sda1`…`sda29` |
| Ядро | mainline 7.2.0-rc6, база `0d8395707`, дерево в `build/src/linux` |
| Прошито в BOOT (`sda7`) | `build/device-backups/boot_upmcrs.img` (md5 `33b0577fd3214a030f566660a2c9cf33`) |
| UFS/PHY в ядре | модулями (`=m`), в blacklist, грузятся опытом через `insmod` |

Цепочка загрузки: `S-Boot → uniLoader → mainline → initramfs → switch_root →
systemd → GDM → GNOME`. Ядро S-Boot читает с внутренней UFS (у него свой
драйвер), корневая ФС — пока с карты.

### 1.1. Что в итоге решило дело

Правок было много, но выяснить, какая именно вылечила линк, помог сам опыт:
регистры HCI читались **до** загрузки драйвера.

- **Не решило:** обе вендорские записи HCI, на которые ставилась главная
  ставка. `HCI_UFS_ACG_DISABLE` (0xFC) и `HCI_MPHY_REFCLK_SEL` (0x108) уже
  читались как `0x1` — S-Boot выставляет их сам, наши записи были
  подтверждением, а не лечением.
- **Решило** что-то из остального набора: таблица калибровки PMA под 8895,
  шаг между линиями `0x140` вместо `0xC0`, селектор линий RX (снятый
  `BROKEN_RX_SEL_IDX`), период такта PCS 12 нс вместо 7, и снятый
  `UFSHCI_QUIRK_BROKEN_HCE`. Разделить их между собой отдельными прогонами
  не пробовали — линк встал сразу со всем набором.
- **Побочное подтверждение таблицы:** S-Boot оставляет в PMA
  `0x110 = 0xb5`, `0x164 = 0x58`, `0x250 = 0xb5` — ровно те значения,
  которые пишет новая таблица. Значит адресация и содержимое верные.
- **Последним куском** оказался `UPMCRS`: линк и обмен UPIU уже работали,
  устройство отвечало, но смена режима питания объявлялась неудачной.
  Прерывание о завершении приходило, а статус читался нулём — у Exynos8895
  поля `UPMCRS` в стандартном `HCS` нет, результат лежит в регистре UniPro
  `0x78EC`. Даунстрим включает под это `UFSHCD_QUIRK_GET_UPMCRS_DIRECT`
  ровно для `hw_rev 0004`. У нас это хук `vops->get_upmcrs` и флаг
  `EXYNOS_UFS_OPT_UPMCRS_IN_UNIPRO`.

### 1.2. Переезд состоялся

Debian перенесён на `sda29` и **грузится без карты вообще**. Подробности —
в [progress-log.md](progress-log.md), запись от 2026-08-08. Коротко:

- корень `sda29`, метка **`linuxroot`** (не `userdata`: у microSD метка
  ровно та же, и `LABEL=userdata` в fstab указывал бы на две разные ФС);
- `CONFIG_SCSI_UFS_EXYNOS=y`, `CONFIG_PHY_SAMSUNG_UFS=y`, blacklist снят;
- initramfs ищет корень в порядке `sda29`, `mmcblk0p1`, `mmcblk0`;
- скрипты обвязки монтируют `sda29` в `/mnt/linuxroot`, а не карту;
- **`tar` из TWRP на копировании rootfs не годится** — busybox 1.22.1
  разрастается до 3 ГБ и его убивает OOM-killer всегда на 348 МБ. Только
  `cp -a`.

### 1.3. Что осталось по UFS

1. Снять отладочные `UFSMARK`: со встроенным драйвером они срабатывают на
   каждой загрузке, и каждый стоит `mdelay(60)` плюс перерисовку fbcon.
2. Починить путь очистки после ошибки: `exynos_ufs_ctrl_clkstop` падает по
   синхронному внешнему аборту в `ufshcd_hba_exit`. Пока probe успешен, это
   не мешает, но дефект настоящий.
3. Подготовить правки к отправке в апстрим. Кандидаты, годные как есть:
   `phy-exynos8895-ufs.c` + `samsung,exynos8895-ufs-phy`,
   `exynos8895_ufs_drvs` с его хуками, чтение `pclk-freq-avail-range`,
   хук `vops->get_upmcrs`.

## 2. Что уже исправлено (обе правки годятся в апстрим)

### 2.1. Паника от SError на защищённом UFSP

`exynos_ufs_config_smu()` пишет в блок защиты UFS. На Exynos8895 он
принадлежит защищённому миру: чтение из EL1 отдаёт нули, **запись поднимает
асинхронный внешний аборт**, ядро паникует и гасит остальные ядра.

```
SError Interrupt on CPU5, code 0x00000000bf000002
pc : exynos_ufs_config_smu+0xc0/0xe8 [ufs_exynos]
Kernel panic - not syncing: Asynchronous SError Interrupt
SMP: stopping secondary CPUs
```

Именно это годами выглядело как «телефон намертво завис в случайном месте»:
вывод паники не успевал дойти до fbcon.

**Правка:** свой `exynos8895_ufs_drvs` в `drivers/ufs/host/ufs-exynos.c` с
флагом `EXYNOS_UFS_OPT_UFSPR_SECURE` (заведён в апстриме ровно для этого,
его использует `gs101`) и compatible `samsung,exynos8895-ufs`.

### 2.2. Отсутствие `freq-table-hz` обнуляло все тайминги M-PHY

`ufshcd_parse_clock_info()` без этого свойства выходит **раньше**, чем
добавит в `hba->clk_list_head` хоть один клок:

```c
sz = of_property_count_u32_elems(np, "freq-table-hz");
if (sz <= 0) {
	dev_info(dev, "freq-table-hz property not specified\n");
	goto out;          /* список остаётся ПУСТЫМ */
}
```

Дальше: `exynos_ufs_get_clk_info()` видит пустой список, уходит по `goto out`
и возвращает **0, то есть успех**, оставив `pclk_rate` и `mclk_rate` нулями.
На arm64 деление на ноль не ловится, а тихо даёт ноль — период стал нулевым,
делитель PWM не нашёлся, и все тайминги M-PHY посчитались от нулевой
частоты.

**Правка:** `freq-table-hz = <0 0>, <0 0>;` в узел `ufs` (так у `exynos7`,
`exynosautov9`, `exynosautov920`, `gs101` — у **всех** in-tree узлов UFS).

Проверка, что подействовало: атрибуты в логе стали настоящими
(`0x317 val 0x28`, `0x355 val 0x1a`, `0x354 val 0x41`, `0x353 val 0x9a`)
вместо нулей, и пропала строка `failed to decide pwm clock divider`.

## 3. Хронология: что было сломано (историческая часть)

> Разделы 3, 4 и 8 описывают путь к решению и оставлены как есть — они
> объясняют, почему код выглядит именно так. Актуальное состояние — в
> разделе 1.

### 3.1. Первый барьер: UIC не оживал после сброса

**UIC-интерфейс не оживает после того, как драйвер сбрасывает контроллер.**

```
UFSTRACE: hce_enable_notify status=0 / status=1     <- HCE проходит
UFSTRACE: link_startup_notify -> pre_link enter
dme-set: attr-id 0x9540 val 0x1 failed 0 retries    <- и дальше падает всё
UFSTRACE: exynos_ufs_phy_init -> phy_init -> power_on -> calibrate
uic cmd 0x16 with arg3 0x0 completion timeout        (0x16 = DME_LINK_STARTUP)
link startup failed -110
```

### Ключевое наблюдение

`HCS` **до** загрузки драйвера = `0x0000000f`:

| Бит | Имя | Значение |
|---|---|---|
| 0 | DP | устройство подключено |
| 1 | UTRLRDY | очередь запросов готова |
| 2 | UTMRLRDY | очередь задач готова |
| 3 | **UCRDY** | **UIC-интерфейс готов** |

Регистры PMA самого PHY при этом держат осмысленные значения (`0x88`, `0x88`).

**S-Boot оставляет контроллер и PHY полностью настроенными, с поднятым
линком** — он же только что прочитал через них ядро. Железо исправно.
Ломается оно ровно тогда, когда наш драйвер сбрасывает контроллер и
поднимает линк заново по сценарию от Exynos7420.

## 4. Что тогда планировалось (всё сделано, см. раздел 9)

### 4.1. Настоящий PHY-драйвер под Exynos8895

Сейчас в dts стоит шаблон `samsung,exynos7-ufs-phy`, а это другой чип
(Exynos7420). Конкретно нужно:

- **Своя таблица калибровки** из даунстрима. Мы используем
  `exynos7_ufs_phy_cfgs` из `drivers/phy/samsung/phy-exynos7-ufs.c` — набор
  магических чисел, посчитанный под 7420.
- **Смещение регистра изоляции в PMU.** У нас `0x724` (из даунстрима,
  `0x16480724` под узлом `ufs-phy-sys`), у драйвера по умолчанию `0x720`
  (регистр 7420). **Никем не проверено** — прочитать PMU из userspace не
  вышло (bus error), нужен другой способ.
- **Модель тактов.** У exynos7 их четыре (`tx0_symbol_clk`, `rx0_symbol_clk`,
  `rx1_symbol_clk`, `ref_clk`), у нас три из них — фиктивные `&oscclk`.
  Все Samsung SoC новее 7420 (autov9, autov920, gs101) используют **один**
  `ref_clk`. Проверено ранее: у Exynos8895 в даунстриме таких гейтов нет
  вообще, есть только 4 UFS-клока (aclk/fmp/unipro + мультиплексор).
  Вывод: четырёхтактовая модель для нас неверна изначально.

Источник даунстрима: `Dyneteve/android_kernel_samsung_universal8895`,
оттуда уже брались адреса регистров (подтвердились независимо).

### 4.2. Проверить, не мешают ли quirks от exynos7

`exynos8895_ufs_drvs` унаследовал `quirks`/`opts` от `exynos_ufs_drvs` целиком
(в том числе `UFSHCI_QUIRK_BROKEN_HCE`, `EXYNOS_UFS_OPT_SKIP_CONNECTION_ESTAB`,
`EXYNOS_UFS_OPT_USE_SW_HIBERN8_TIMER`). Осознанно: меняли одно за раз. Стоит
перебрать — особенно `EXYNOS_UFS_OPT_SKIP_CONFIG_PHY_ATTR`, который у всех
новых SoC выставлен, а у нас нет (именно он отключает те самые `dme-set`,
что сейчас падают пачками).

### 4.3. Мелкий отдельный дефект

Путь очистки после ошибки сам неисправен: `insmod` завершается по SIGSEGV, в
логе стек через `ufshcd_setup_clocks+0x100 → ufshcd_hba_exit → ufshcd_init`.
К молчанию UIC отношения не имеет, но чинить придётся.

## 5. Как работать с устройством

### 5.1. Цикл эксперимента

```bash
# телефон в TWRP
./scripts/arm-experiment.sh experiments/NN-имя.sh
./build/tools/platform-tools/adb reboot
# ждём загрузки; если завис — Power + Volume Down, зайти в TWRP
./scripts/collect-lab.sh
```

Флаг `ARMED` снимается **на устройстве до запуска** опыта — зависание не
превращается в петлю перезагрузок.

### 5.2. Пересборка и прошивка

```bash
./scripts/build-boot.sh <имя> --kernel   # ядро + dtb + МОДУЛИ + boot.img
./scripts/push-modules.sh                # обязательно! модули живут в rootfs
ADB=./build/tools/platform-tools/adb
$ADB push build/device-backups/boot_<имя>.img /tmp/b.img
$ADB shell 'dd if=/tmp/b.img of=/dev/block/sda7 bs=4096 && sync'
# сверить md5 обязательно:
$ADB shell 'dd if=/dev/block/sda7 bs=512 count=68992 2>/dev/null | md5sum'
```

### 5.3. Чтение логов

```bash
./scripts/read-journal.sh --list-boots
./scripts/read-journal.sh --boot=<id> -k -o short-monotonic | grep UFSTRACE
```

Перед каждым монтированием карты: `e2fsck -fp /dev/block/mmcblk0p1`
(после форс-ребутов ФС грязная).

## 6. Грабли, на которые уже наступали

- **Экран врёт.** fbcon на 1440x2960 рисует строку на порядки медленнее,
  чем они печатаются, поэтому на экране остаётся последняя ОТРИСОВАННАЯ
  строка, а не последняя выполненная. Один раз это стоило целого дня:
  экран показывал остановку в `ufshcd_alloc_host()`, где нет ни одного
  обращения к железу. Верить только journal и ramoops.
- **Кнопка питания в загруженной системе = штатное выключение.**
  `gpio-keys` отдаёт нажатие как обычное событие ввода, `systemd-logind`
  превращает его в poweroff (в логе видно `Syncing filesystems` и
  `System Power Off`). Выглядит это как «лог вдруг продолжился», хотя на
  деле начиналась остановка сервисов — на это уже один раз купились и
  придумали неверное объяснение про отложенный printk.

  Практически: **во время опыта кнопки не трогать**, иначе он оборвётся на
  середине. Зато карта размонтируется начисто, и журнал дожимается на диск —
  именно поэтому `e2fsck` всё это время не находил повреждений.

  Настоящий аппаратный сброс, когда ядро действительно мертво, — Power +
  Volume Down удержанием ~7 секунд, мимо systemd.
- **`make Image dtbs` не собирает модули**, а `modules_install` их не
  пересобирает. Разложить старые `.ko` — значит полдня читать трассировку,
  которой в них нет. В `build-boot.sh` это уже исправлено.
- **Выкладывание модулей в rootfs меняет поведение загрузки:** udev видит
  OF-modalias у включённых в dts узлов и грузит их сам. UFS поэтому в
  blacklist (`/etc/modprobe.d/dreamlte-ufs.conf`), эксперименты используют
  `insmod` с явным путём.
- **Функция, возвращающая 0 при пустом списке, делает маркер «ok» ложным.**
  Наш `E8 get_clk_info ok` честно печатался, пока частоты были нулями.
- **`dev_info` о ненайденном свойстве — не пометка, а сообщение об обрыве
  разбора.** `freq-table-hz property not specified` висела в логе с первой
  удачной загрузки драйвера.
- **ramoops работает**, но данные появляются на **следующей** загрузке —
  не надо перезагружаться дважды подряд, иначе они теряются.
- **adb shell портит бинарные данные**, для чтения разделов только
  `adb exec-out`.
- **У загруженной системы нет ни USB, ни сети, ни клавиатуры** — всё
  готовится заранее из TWRP.

## 8. Развилка разрешена: UniPro отвергает атрибуты Exynos7420

Печать кода возврата дала однозначный ответ:

```
dme-set: attr-id 0x9540 val 0x1 failed 0 retries (ret=1)
```

**`ret=1` — это `INVALID_MIB_ATTRIBUTE`,** стандартный код отказа UniPro
«такого атрибута нет». Не таймаут. Шина полностью исправна: она отвечает,
и отвечает отказом.

Это снимает подозрение с PHY целиком и переносит его на набор атрибутов:

- `0x9540` = `PA_DBG_OV_TM` — вендорский «режим отладочного доступа»
  **Exynos7420**. Им `exynos_ufs_enable_ov_tm()` открывает доступ к тестовым
  атрибутам M-PHY. У Exynos8895 его нет.
- Раз доступ не открылся, следом отвергаются и все тестовые атрибуты, что
  пишет `exynos_ufs_config_phy_time_attr()`: `0x316`, `0x317`, `0x340`,
  `0x341`, `0x352`…`0x355`.
- У SoC новее 7420 схема другая: вендорский доступ открывается атрибутом
  `0x200` (`ufshcd_dme_set(hba, UIC_ARG_MIB(0x200), 0x40)` в начале
  `gs101_ufs_pre_link` и `0x0` в конце). `PA_DBG_OV_TM` там не используется
  вообще.

Подтверждение косвенное, но сильное: `DME_RESET` (0x14) и `DME_ENABLE`
(0x12) — тоже UIC-команды — проходят **успешно**. Работает всё, кроме
несуществующих атрибутов.

### Что сделано в ответ

В `exynos8895_ufs_drvs`:

- добавлен `EXYNOS_UFS_OPT_SKIP_CONFIG_PHY_ATTR` — отключает
  `config_phy_time_attr()`/`config_phy_cap_attr()`, то есть ровно те пачки
  отвергаемых записей. Этот флаг выставлен у **всех** Samsung SoC новее
  7420 (autov9, autov920, gs101, fsd);
- убраны хуки `.pre_link`/`.post_link` от exynos7 — они целиком построены
  вокруг `PA_DBG_OV_TM`.

Расчёт на то, что S-Boot оставляет PHY уже настроенным (`HCS = 0xf`,
`UCRDY` выставлен, PMA держит осмысленные значения), поэтому линк может
подняться и на умолчаниях.

### Если не поднимется — следующий шаг

Написать `exynos8895_ufs_pre_link()` по образцу `gs101_ufs_pre_link()`:
открыть вендорский доступ через `0x200`, запрограммировать период тактов
(`VND_TX_CLK_PRD`/`VND_RX_CLK_PRD` = `DIV_ROUND_UP(NSEC_PER_SEC, mclk_rate)`)
и значения line-reset, закрыть доступ, затем выставить стандартные атрибуты
линка (`PA_LOCAL_TX_LCC_ENABLE`, `N_DEVICEID`, `T_CONNECTIONSTATE` и т.д.).
Смещения `VND_*` у gs101 общие для нового поколения M-PHY Samsung — есть
шанс, что подойдут и здесь; сверять с даунстримом
`Dyneteve/android_kernel_samsung_universal8895`.

### Результат: шум ушёл, осталась одна чистая ошибка

После отключения вендорских атрибутов 7420 **все `INVALID_MIB_ATTRIBUTE`
исчезли из лога полностью.** Осталась ровно одна строка:

```
UFSTRACE: pre_link enter -> exynos_ufs_phy_init -> phy_init -> power_on -> calibrate
exynos-ufshc 11120000.ufs: uic cmd 0x16 with arg3 0x0 completion timeout
exynos-ufshc 11120000.ufs: link startup failed -110
```

Это важный сдвиг качества: раньше отказы сыпались пачками и маскировали
происходящее, теперь отказ ровно один и он говорит конкретную вещь.

`0x16` = `DME_LINK_STARTUP`. Он **не отвергается** (кода отказа нет) — он
**не завершается**: команда выдана, прерывание о завершении не приходит.
Это уже не «неправильный атрибут», а «M-PHY не устанавливает связь с
устройством». Вот теперь подозрение на PHY законно.

Отметим: `exynos_ufs_pre_link()` (общая функция драйвера, не хук) всё равно
выполняется — она делает `exynos_ufs_config_unipro()` и
`exynos_ufs_phy_init()`. Наш `drv_data->pre_link` теперь пуст, но эта часть
никуда не делась и тоже посчитана от `mclk_rate`.

### Приоритет работ после этого прогона

1. **`exynos8895_ufs_pre_link()` по образцу `gs101_ufs_pre_link()`** —
   гейт `0x200` вместо `PA_DBG_OV_TM`, программирование `VND_TX_CLK_PRD` /
   `VND_RX_CLK_PRD` (= `DIV_ROUND_UP(NSEC_PER_SEC, mclk_rate)`), значения
   line-reset, затем стандартные атрибуты линка. Скорее всего именно этого
   сейчас и не хватает: мы убрали настройку 7420, но ничего не поставили
   взамен.
2. **Проверить `exynos_ufs_config_unipro()`** — что она пишет в регистры
   UniPro и подходят ли эти смещения 8895.
3. **PHY-калибровка под 8895** — только если пункты 1–2 не помогут.
4. Отдельно: путь очистки после ошибки неисправен (`insmod` уходит в
   SIGSEGV, стек через `ufshcd_setup_clocks+0xfc → ufshcd_hba_exit`).

### Прогон с `exynos8895_ufs_pre_link`: атрибуты приняты, линк не встал

```
UFSTRACE: 8895 pre_link: mclk=166562500
UFSTRACE: 8895 pre_link готов
exynos-ufshc 11120000.ufs: uic cmd 0x16 with arg3 0x0 completion timeout
   (повторяется 4 раза — retries)
exynos-ufshc 11120000.ufs: link startup failed -110
```

**Ни одного `ret=1`.** Все вендорские атрибуты, записанные через гейт
`0x200`, приняты UniPro — то есть схема gs101 для этого чипа верна, и
предположение подтвердилось. Но `DME_LINK_STARTUP` по-прежнему не
завершается.

Значит остаётся физика линка, и круг сузился до трёх вещей — все три
относятся к PHY, и все три перечислены в разделе 4.1:

1. таблица калибровки от Exynos7420 в `phy-exynos7-ufs.c`;
2. непроверенное смещение регистра изоляции в PMU (`0x724` против `0x720`);
3. три фиктивных `&oscclk` вместо настоящих тактов PHY (и, вероятно,
   вообще неверная четырёхтактовая модель).

Плюс не проверено, подходят ли 8895 смещения регистров, куда пишет
`exynos_ufs_config_unipro()`.

### Побочно закрыт вопрос с GNOME

Рабочий стол не появлялся не из-за поломки:

```
org.gnome.Shell@wayland.service: start operation timed out. Terminating.
org.gnome.Shell@wayland.service: Failed with result 'timeout'.
```

`gnome-shell` не падал — его **убивал systemd по таймауту запуска** (90 с по
умолчанию). На llvmpipe при 1440×2960 первый кадр рисует процессор, и когда

Исправлено: `TimeoutStartSec=600` для `org.gnome.Shell@wayland.service`
(в `setup-rootfs-session.sh`, пункт 11). Плюс вывод опыта больше не
дублируется в `/dev/kmsg` — каждая такая строка перерисовывала fbcon
целиком и отбирала экран у сеанса.

## 9. Даунстрим Samsung: где что лежит

Даунстрим склонирован в `~/build/src/downstream-8895` (репозиторий
`Dyneteve/android_kernel_samsung_universal8895`, `--depth 1`).

**Главное про его устройство:** отдельного PHY-драйвера у Samsung нет, PMA
программируется прямо из драйвера UFS, а сама последовательность старта
лежит **не в коде, а в device tree**. Узел `ufs@0x11120000` в
`arch/arm64/boot/dts/exynos/exynos8895.dtsi` (строки ~762–1045) содержит:

| Свойство | Когда применяется | Куда уехало у нас |
|---|---|---|
| `phy-init` | до `DME_LINK_STARTUP` | записи `PHY_PMA_*` → `phy-exynos8895-ufs.c`, остальные → `exynos8895_ufs_pre_link()` |
| `post-phy-init` | после старта линка | `exynos8895_ufs_post_link()` |
| `calib-of-hs-rate-a/b` | перед сменой режима на HS | `exynos8895_pre_pwr_hs_cfg[]` + `exynos8895_ufs_pre_pwr_change()` |
| `post-calib-of-hs-rate-b` | после смены режима | хук `wait_for_cdr` в PHY-драйвере |
| `calib-of-pwm`, `pre-clk-off`, `post-clk-on`, `lane1-sq-off` | PWM, гашение тактов, отключение линии 1 | пока не перенесены |

Каждая запись — четвёрка «адрес, значение, маска режимов, тип». Тип
(`PHY_PMA_COMN`, `PHY_PMA_TRSV`, `PHY_PCS_RX`, `PHY_PCS_TX`,
`UNIPRO_STD_MIB`, `UNIPRO_DBG_MIB`, `UNIPRO_DBG_PRD`, `COMMON_WAIT`,
`PHY_CDR_WAIT`, …) определяет, куда идёт запись; разбирает их
`exynos_ufs_config_uic()` в `drivers/scsi/ufs/ufs-exynos.c`. Константы типов
— в `include/dt-bindings/ufs/ufs.h`.

### 9.1. Адресация PMA у Exynos8895

Это отдельный источник ошибок, поэтому явно (`drivers/scsi/ufs/ufs-exynos.h`,
ветка `!EXYNOS7420 && !EXYNOS8890`):

```c
#define PHY_PMA_COMN_ADDR(reg)		(reg)
#define PHY_PMA_TRSV_ADDR(reg, lane)	((reg) + (0x140 * (lane)))
```

То есть в вендорских таблицах смещения **уже байтовые**, а шаг между линиями
`0x140` байт. Блок COMN занимает `0x000..0x0BF`, TRSV линии 0 начинается с
`0x0C0`, линии 1 — с `0x200` (отсюда подписи вида `TRSVx_14(0x110/0x250)`).

Макросы `phy-samsung-ufs.h` в mainline принимают **номер регистра** и сами
домножают на 4, поэтому в `phy-exynos8895-ufs.c` все смещения поделены на 4,
а шаг линии равен `0x140 / 4 = 0x50`. Байтовый адрес из даунстрима оставлен
в комментарии к каждой строке — сверка механическая.

Для сравнения: у exynos7 `PHY_TRSV_CH_OFFSET` = `0x30` регистров, то есть
`0xC0` байт. Пока мы использовали шаблон 7420, все записи для линии 1
уезжали не туда.

### 9.2. Что подтвердилось из прежних догадок

- **Изоляция PHY = PMU `0x724`.** Литерал `0x16480724` в подузле
  `ufs-phy-sys` плюс место записи: `exynos_ufs_ctrl_phy_pwr()` делает
  буквально `writel(!!en, ufs->phy.reg_pmu)`. Вопрос закрыт.
- **Symbol-клоков PHY не существует.** Узлу `ufs` отданы ровно два клока:
  `GATE_UFS_EMBD` (aclk) и `UFS_EMBD` (unipro). Четырёхтактовая модель
  `samsung,exynos7-ufs-phy` для 8895 неверна в принципе.
- **Атрибуты M-PHY от 7420 не нужны:** `exynos_ufs_config_phy_time_v()` и
  `exynos_ufs_config_phy_cap_attr()` для `hw_rev >= UFS_VER_0004`
  (8895 — это 0004) выходят первой же строкой. `SKIP_CONFIG_PHY_ATTR`
  выставлен верно.
- **`establish_connt` тоже пропускается**, а `N_DeviceID` /
  `T_ConnectionState` пишутся до старта линка — как у `gs101_ufs_pre_link()`.

### 9.3. Пять ошибок, которые нашлись при сверке

1. **`UFSHCI_QUIRK_BROKEN_HCE` был лишним.** Даунстрим включает обход HCE
   (`UFSHCD_QUIRK_USE_OF_HCE`) **только для `UFS_VER_0003`, то есть для
   Exynos8890**. У нас контроллер поднимается штатной записью HCE.
2. **`EXYNOS_UFS_OPT_BROKEN_RX_SEL_IDX` был лишним** — с ним
   `rx_sel_idx = 0`, и все атрибуты PCS RX уходили с селектором
   передатчика. У даунстрима `RX_LANE_0 = 4`. Отказа в логе не видно: за
   гейтом `0x200` шина принимает любой адрес.
3. **Период такта PCS был вдвое неверным.** Даунстрим пишет в
   `VND_RX_CLK_PRD`/`VND_TX_CLK_PRD` период **pclk** простым делением, а не
   период mclk с округлением вверх (формула gs101). При
   `pclk-freq-avail-range = <70000000 166000000>` частота 166.5625 МГц
   делится ровно один раз → APB UniPro 83.28 МГц → период 12 нс, а не 7.
4. **Не хватало двух вендорских записей HCI** (блок 0xF8+, которого у 7420
   нет): `HCI_UFS_ACG_DISABLE` (0xFC бит 0, выключение HWACG на время
   инициализации) и `HCI_MPHY_REFCLK_SEL` (0x108 бит 0, выбор пути опорного
   такта M-PHY). Вторая — главный подозреваемый по таймауту
   `DME_LINK_STARTUP`: без опорного такта PLL не захватывается, и команда
   не завершается вообще.
5. **Шаг между линиями PMA** — см. 9.1.

- Ничего для сборки: тулчейн, uniLoader, busybox, ядро уже в `build/`.
